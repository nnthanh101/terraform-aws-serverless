# Security baseline: the controls, their cost and why

The 40 features the product owner and the cloud architect weighed for one account's security baseline on 2026-09-24, and what the module does with each. They agreed 35 in the first round and the other 5 (F09, F24, F29, F37, F39) in a second; a third reviewer re-checked every premise against AWS documentation or the code and found none false. Where the owner ruled against the round, the section "Where the owner ruled against the round" says so, with the reason.

How to read the catalogue:

- **Single account**: what this module does in one account. *on* is built and on by default; *switch, off* is built behind a switch that is off by default; *not built* is left out on purpose.
- **Landing zone**: where the control belongs once the account sits in an organization. This module does not build that.
- **US$ a month**: ap-southeast-6, from the round, with its assumption. The prices behind the figures are dated at the end.
- **Evidence**: a line of `bash scripts/security-baseline.sh verify` (named by its id), or the read-only command shown. Every command reads; none writes. A switch's line reads `off` only when the service itself says so, and a read that fails is a failure; with `--expect` (QUICKSTART, step 9), a switch the root's `controls` output says is on fails when it reads off.

The module reference, inputs and outputs are in [README.md](README.md); the deploy steps belong to the root that calls the module.

## Where the owner ruled against the round

- **F09, the refused-calls alarm: on.** The round said off by default: the read-only automation is refused secret and data reads on purpose, and those routine refusals can reach 5 in 5 minutes and page the same topic as production alarms. The owner ruled it on, because refused calls are the first sign of someone probing the account, and gave it its own switch, `unauthorized_api_calls_alarm_enabled`. Its metric and dashboard widget stay when it is off.
- **F15, the dashboard: built.** The round said not built, since nobody was named to read it and alerts reach the owner by email. The owner ruled it built: the demonstrations open it, and it shows who was refused, which the refused-calls alarm alone does not.
- **F22, the web ACL: a switch in the baseline, off.** The round said not to build a second web ACL: HTTP APIs cannot take one, and digital-yr12's distribution has its own (`site_waf_enabled`). The owner kept the switch, off by default, for an account's REST API stage, load balancer or other distribution. A distribution takes one web ACL: use this one or digital-yr12's, not both.
- **F12 and F33 to F35, the people roles: they exist only when someone is named.** The round said not built. BreakGlassAdmin, as the round saw it, could not be assumed: Identity Center sessions carry no MFA key, and the root user cannot assume a role. SecurityAuditor and DeveloperTemplate trusted the whole account with an MFA condition that sessions without an MFA key pass, so the apply roles could have assumed them. The owner kept all three behind named principals, empty by default. BreakGlassAdmin trusts only the IAM users named, who sign in with MFA; its alarm (F12) comes with it. The other two pass only the principals named, by `aws:PrincipalArn`; the plan refuses bare wildcards and the `gha-*` and `workload/*` roles; and SecurityBaselineProtect denies the apply roles `sts:AssumeRole` on all three names, whether or not the roles exist. Until someone is named, the break-glass path is the root user with MFA, which F08 alarms.

## What is not built and why

- **F06, colder storage for trail files.** Nearly every trail file is under 128 KB, which S3 does not move by default; forcing it adds request charges and 40 KB of overhead per object to save under US$0.05 a month. Expiry lives in F04's rule.
- **F14, the other eleven CIS alarms.** Five watch VPC resources the account does not use; the console sign-in filters match IAM users, of which there are none; Organizations events land in the management account; F13 and F36 already cover trail and key tampering.
- **F20, Config rules for the root user.** AWS advises against them where global IAM types are not recorded, and ap-southeast-6 cannot record them. `verify` reads the root user's MFA and keys for free (`root-account`), and F08 alarms on any use.
- **F24, the unused-access analyzer.** US$2 to US$4 a month, 20 to 40% of the US$10 a month that `budget_usd` in records/adoption.md sets for each environment, to review roles Terraform already defines in a one-person account. A yearly manual access review is the evidence; the free external-access analyzer (F23) stays.
- **F29, the default VPC in Terraform.** Nothing uses a VPC, and adopting one creates a default VPC where none exists. Delete it once when the account is made; F28 already empties its default security group.
- **F30, VPC flow logs.** They would log a VPC that carries no traffic. Ship them with the first VPC a workload creates.
- **F32, SupportAccess.** An Identity Center permission set with AWSSupportAccess meets CIS 1.17 without an IAM role nobody uses; the apply roles already hold `support:*` through PowerUserAccess.
- **F37, CloudTrail Insights.** Pipeline applies and routine refusals drive both the call rate and the error rate, so it would report noise, not signal. GuardDuty is the anomaly switch.
- **F39, a landing-zone mode.** Switching mode would plan the destruction of the trail, detector and recorder, which the organization's baseline policy denies once the account sits in an organizational unit. A mode tested only on mocks would be a gate that passes whatever it is given. The move is its own change (below).

## Single account and landing zone

This module is for one account that is not in a landing zone, or not yet. In a landing zone:

- Member accounts do not duplicate the organization trail or the CIS alarms. The organization trail, in the management account or a CloudTrail delegated administrator, writes to the Log Archive account, and the alarms read its log group centrally.
- GuardDuty, Security Hub, Inspector and an organization Access Analyzer run from a delegated administrator in the security tooling account, which enables every member.
- A member keeps its account settings (F25 to F28, F31), its own key and topic for workload alarms, SecurityBaselineProtect on its apply roles, and an AWS Config recorder, since recorders have no organization-wide auto-enable.
- `verify --mode landing-zone` reads a member that way: the trail family and the detectors report `off (landing-zone mode: the organization covers it)`.
- Until the landing-zone change below, a member account that an organization trail covers should not apply this root: the baseline trail would be a second copy of management events, billed at 2.00 USD per 100,000. `preflight` warns when it finds an organization trail.

Moving this account into the landing zone is its own change, in this order: turn the organization trail on and switch this trail off in the same apply (this module has no trail switch today; that change adds one), settle how the account keeps its Config recorder, then move the account into its organizational unit. Once it is there, the baseline policy denies deleting a trail, detector or recorder.

## Break-glass runbook

When nobody is named in `break_glass_principal_arns`, the break-glass path is the root user, signed in with MFA; the root-usage alarm emails the topic on every call it makes.

Before any emergency: right after the apply that names a user in `break_glass_principal_arns`, the administrator reads the external ID (`tc terraform -chdir=infra/security-baseline output -raw break_glass_external_id`, QUICKSTART, "Turn a switch on") and stores it with that user's sealed break-glass credentials and MFA device. The only other copy is in this root's state, and in an emergency no one may be able to read that state: reading it takes the administrator's access, which may be what failed.

When BreakGlassAdmin exists:

1. Only an IAM user named in `break_glass_principal_arns` can use it, signed in with MFA within the last hour.
2. Take the external ID from where it was stored with your sealed credentials. It is not a secret: AWS designed external IDs against a confused deputy, not as a password. The controls that matter are MFA within the hour, the one-hour session and the alarm on every use.
3. Assume the role for one hour:

   ```sh
   aws sts assume-role --role-arn arn:aws:iam::<account id>:role/BreakGlassAdmin \
     --role-session-name <your name>-<ticket or reason> --external-id <external id> \
     --serial-number <your MFA device ARN> --token-code <code> --duration-seconds 3600
   ```

4. The break-glass-use alarm emails the alerts topic. Reply to it with the reason, so the record says why.
5. Afterwards, list what the session did from the trail's log group. In CloudWatch Logs Insights on `<service>-shared-cloudtrail`: `filter userIdentity.arn like /BreakGlassAdmin/ | fields eventTime, eventSource, eventName, errorCode | sort eventTime asc`.
6. When a named person leaves, remove their ARN from `break_glass_principal_arns` and apply.

## Known gaps

- **Detectors and settings cover the home Region only.** GuardDuty, Security Hub, Config, Inspector, the analyzer, EBS default encryption, snapshot block public access, the SSM sharing setting and the default security group are set in the home Region. The trail and its alarms see every enabled Region. The apply roles have no Region deny yet (templates/bootstrap README, "Where least privilege stands").
- **The apply and workload roles can still read the trail's events, and can let an AWS service write into its log group.** The workload boundary allows `logs:*`, `sns:*` and `s3:*`. On names that start `security-baseline-` (the default `name_prefix`), it denies workload roles every CloudWatch Logs action on the trail log group except reading and querying its events (`logs:Get*`, `logs:Describe*`, `logs:List*`, `logs:FilterLogEvents`, `logs:StartQuery`, `logs:StopQuery`, `logs:GetQueryResults`, `logs:StartLiveTail`, `logs:StopLiveTail`). So they cannot delete the group or change its retention, metric filters, key, data-protection policy, transformer, deletion protection or tags, copy its events out with a subscription filter or an export task, or write events of their own into it. That deny names only those log groups' ARNs, and only CloudWatch Logs actions name a log group, so no other service's call matches it. On the topic and the findings rules the boundary denies them every SNS and EventBridge action except reading (`sns:Get*`, `sns:List*`, `events:Describe*`, `events:List*`): no deleting, re-pointing, subscribing, unsubscribing, publishing or untagging. SecurityBaselineProtect denies the apply roles the same on the trail log group. Both deny the account-level CloudWatch Logs policies, `logs:PutAccountPolicy` and `logs:DeleteAccountPolicy`, on every resource: an account data protection policy masks the data it names "at all egress points, including CloudWatch Logs Insights, metric filters, and subscription filters" (https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/mask-sensitive-log-data.html), and an account transformer policy changes the events that metric filters read (https://docs.aws.amazon.com/AmazonCloudWatchLogs/latest/APIReference/API_PutAccountPolicy.html), so either could stop the alarms matching the trail's events; an account subscription filter policy would copy them out. Both also deny the account's S3 Block Public Access setting (`s3:PutAccountPublicAccessBlock`): the boundary's ProtectAccountPublicAccessBlock to workload roles, SecurityBaselineProtect to the apply roles; `verify`'s `account-pab` line reads it back. What stays open: both kinds of role can read and query the trail's events, which name people and IP addresses; both can still set a CloudWatch Logs resource policy on the group (`logs:PutResourcePolicy`, which IAM authorizes against no resource, so a deny on the group's ARN cannot reach it), and such a policy lets an AWS service write events into the group, for example EventBridge through a rule the role creates, so while those events arrive the trail-delivery alarm stays quiet even if CloudTrail's own delivery has stopped; the name match protects the baseline only while the root's `service` keeps its default; an account bootstrapped before this change gets these denies only when the administrator re-applies the bootstrap. The resource-policy route is an accepted risk (Open routes, below). Publishing to the topic needs the baseline key, which the key policy denies to `workload/*` roles. The trail files in the bucket stay out of the workload roles' reach and hold only what CloudTrail wrote, and the trail-delivery alarm fires when the group stops receiving events.
- **A subscription confirmed by opening its link can be removed without a signature.** SNS then accepts an unsigned Unsubscribe, which IAM never sees, so SecurityBaselineProtect's `sns:Unsubscribe` deny does not stop it; anyone with the subscription's ARN, such as the unsubscribe link in each alert email, can remove the only subscription, and alerts then reach nobody. QUICKSTART step 7 confirms with `aws sns confirm-subscription --authenticate-on-unsubscribe true` instead, and `verify`'s `subscription` line fails until `ConfirmationWasAuthenticated` is `true`.
- **Injected metric data can raise a false alarm, not silence one.** SecurityBaselineProtect and the workload boundary deny `cloudwatch:PutMetricData` into the `SecurityBaseline` namespace, but a metric filter on another log group, which PowerUserAccess and the workload boundary's `logs:*` allow, can still publish into it. CloudWatch Logs publishes a filter's metric value "each time a matching log is found", and its default value only "during a period when logs are ingested but no matching logs are found" (Creating metrics from log events using filters, Concepts: https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/MonitoringLogData.html). So the refused-calls filter has no default value and its alarm reads the SampleCount, 5 or more in 300 seconds: the number of matching events, whatever value each carries. The other filters (root use, IAM and bucket policy changes, and break-glass use while that role exists) keep a default value of 0, each match writes 1, and their alarms read the Maximum. A datapoint written from elsewhere, by `PutMetricData` or by another log group's filter, adds a sample or raises a maximum; it never lowers either. Every filter publishes, and every alarm on one reads, unit `Count`, so a datapoint in another unit is aggregated apart and those alarms do not read it; without a unit, the PutMetricAlarm API reference says an alarm over a metric published in more than one unit behaves unpredictably. It can raise a false alarm, never hold a real one down. The dashboard's refused-calls widget reads the SampleCount too. Not yet proved on AWS: that the SampleCount reaches one per match when several refused calls land in the same minute (the local emulator serves no metric filters). AC-7 checks it on the first apply: five refused calls one after another within one minute, then the SampleCount and the alarm's Action history (QUICKSTART, Show it in 10 minutes, step 5). If it counts fewer, the alarm goes back to the Sum and the injection gap reopens.
- **Security Hub has control gaps in ap-southeast-6** (no IAM, GuardDuty, Inspector, WAF, CloudFront or HTTP API controls), and **Amazon Inspector is not offered there**; the plan refuses `inspector_enabled = true` in that Region.

## Open routes (audit of 25 Sep)

SecurityBaselineProtect and the workload boundary are deny-lists. The apply roles hold PowerUserAccess, and the workload roles a broad list of services (the boundary's WorkloadServices statement, with `logs:*`, `events:*`, `sns:*` and `s3:*`). On top of those, the baseline denies the switch-off and tamper actions this page lists. A deny-list cannot be shown complete: each of the five read-only audits of 24 and 25 Sep found routes that the audits before it had missed. Following the owner's decision (decision 0010, below), change 0025 closes the four routes the fifth audit found, corrects one test list, and records one accepted risk:

- **The default event bus under a key the caller controls: closed.** SecurityBaselineProtect (in ProtectRuleAndWebAcl) and the workload boundary (ProtectDefaultEventBus) deny `events:UpdateEventBus` on the default bus, in both forms IAM lists for that action: `event-bus/default` and `event-busv2/default/*`. `verify`'s `protect` line simulates only the `event-bus/default` form; the `event-busv2` form is denied because IAM lists it for UpdateEventBus without saying when a request names it, and only the plan-only tests assert it. No condition key narrows the action, so the deny also blocks changes to the bus's logging, dead-letter and description settings; publishing events to the bus stays allowed. Whether a foreign key stops the findings rules matching is not tested: EventBridge documents that a customer managed key on the bus encrypts the rules' patterns and targets, and that events from AWS services stay under an AWS owned key. If a bus is already under a foreign key, the administrator first sets it back to an AWS owned key, because PutRule, PutTargets and DescribeRule on that bus need `kms:Decrypt` on its key.
- **The baseline key's rotation stretched: closed.** ProtectBaselineKey denies `kms:EnableKeyRotation`, which accepts a rotation period of 90 to 2560 days, and `kms:RotateKeyOnDemand`. The bootstrap's ProtectStateKey denies the same two actions on the Terraform state key.
- **The default VPC deleted and made again: closed while `default_security_group_lockdown_enabled` is on.** ProtectAccountSettings denies `ec2:CreateDefaultVpc`, which has no resource-level permission. Deleting the default VPC stays allowed (F29 recommends it). Security Hub's EC2.2 checks the default security group of every VPC, so a workload VPC still manages its own `aws_default_security_group`.
- **GuardDuty and Security Hub invitations: closed.** ProtectDetectors denies `guardduty:Accept*` and `securityhub:Accept*`.
- **Index policies on the trail log group: test lists corrected.** IAM gives `logs:PutIndexPolicy` and `logs:DeleteIndexPolicy` no resource type, so no deny on the log group's ARN reaches them; the module and bootstrap tests no longer list `logs:PutIndexPolicy` as denied. An index policy changes Logs Insights indexing, not the events or the metric filters.
- **A resource policy on the trail log group: accepted risk (owner, 25 Sep 2026).** IAM authorizes `logs:PutResourcePolicy` against no resource, so only a deny on every resource reaches it, and that would break the HTTP API access logs and Step Functions logging the examples use. Such a policy lets an AWS service write events into the group, for example EventBridge through a rule the role creates; while those events arrive, the trail-delivery alarm (IncomingLogEvents) stays quiet even if CloudTrail's own delivery has stopped. Denying only the vended-logs path (`logs:PutDeliveryDestination` by `logs:DeliveryDestinationResourceArn`) would leave the EventBridge path open, so it is not added. What still shows it: `verify`'s `trail-delivery` line reads CloudTrail's own last delivery time (`get-trail-status`), not the group's incoming events; `aws cloudtrail validate-logs` proves the trail files in the bucket are unchanged; and the `PutResourcePolicy` call itself is in the trail. It reopens when IAM gives the action a resource type or a log-group condition key.

These denies reach an account only when the administrator re-applies the bootstrap and then the baseline root (QUICKSTART, "When the baseline's denies change"); `verify`'s `protect` and `default-sg` lines then read the SecurityBaselineProtect denies back from IAM.

Tests strengthened by change 0025 (seeds in `scripts/seeded-defects.sh` prove them, except the NotAction branch and IamRead's Action, which have no seed):

- The bootstrap tests that count grants of `iam:CreateRole` and `iam:PutRolePermissionsBoundary` now match without case, treat IAM's `?` as one character, count an Allow written with NotAction, and read every inline policy of the apply role.
- A bootstrap test pins the Resource of BoundedWorkloadRoles and the Action of IamRead.
- The module test that keeps the trail's delivery role out of the workload path is built from `pipeline_role_patterns`, with a run that uses a custom pattern.
- The module tests on ProtectBaselineIam and DenyAssumingPeopleRoles assert the exact Action and the absence of a Condition.
- Each seeded defect runs on its own and records the assertion that fails.

Closed in the fifth pass: a metric filter on another log group that publishes the baseline's metrics in another unit. Every baseline metric filter publishes, and every alarm on one reads, unit `Count` (Known gaps, above).

**The owner's decision (25 Sep 2026, decision 0010).** Keep PowerUserAccess on the apply roles with the deny statements on top, rather than an allow-list IAM Access Analyzer generates from CloudTrail. Each route an audit finds gets a deny, a plan-only test that fails without it and a seeded defect that proves the test fails, or an accepted-risk entry here that says why there is no deny, what still shows it and what reopens it. A route no audit has found stays open until one does, and a service a workload needs works without a policy change. SecurityBaselineProtect measures 5,976 of IAM's 6,144 characters at its largest configuration after change 0025; the fit test fails closed, and the change whose deny does not fit splits the policy. Revisit when an audit finds a route that only an allow-list could close, or once the dev account holds 90 days of CloudTrail from pipeline applies, the input policy generation reads.
