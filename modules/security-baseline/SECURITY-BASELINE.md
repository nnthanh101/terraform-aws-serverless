# Security baseline: the controls and why

What the module does with each feature in the catalogue for one account, which SOC 2 criteria they serve, how to use the break-glass role and what stays open.

How to read the catalogue:

- **Single account**: what this module does in one account. *on* is built and on by default; *switch, off* is built behind a switch that is off by default; *not built* is left out on purpose.
- **Landing zone**: where the control belongs once the account sits in an organization. This module does not build that.
- **US$ a month**: ap-southeast-6, with its assumption. Prices come from the AWS price list for that Region; recheck them before relying on a figure (see Prices).
- **Evidence**: the id of a check line, or the read-only command shown. The ids are read by the verify script of the calling root; `verify`, `preflight` and the other commands named on this page run from the calling root, not from this module. Every command reads; none writes. A switch's line reads `off` only when the service itself says so, and a read that fails is a failure.

The module reference, inputs and outputs are in [README.md](README.md); the deploy steps belong to the root that calls the module.

## What is not built and why

- **F06, colder storage for trail files.** Nearly every trail file is under 128 KB, which S3 does not move by default; forcing it adds request charges and 40 KB of overhead per object to save under US$0.05 a month. Expiry lives in F04's rule.
- **F14, the other eleven CIS alarms.** Five watch VPC resources the account does not use; the console sign-in filters match IAM users, of which there are none; Organizations events land in the management account; F13 and F36 already cover trail and key tampering.
- **F20, Config rules for the root user.** AWS advises against them where global IAM types are not recorded, and ap-southeast-6 cannot record them. `verify` reads the root user's MFA and keys for free (`root-account`), and F08 alarms on any use.
- **F24, the unused-access analyzer.** US$2 to US$4 a month, a large share of a small environment budget, to review roles Terraform already defines in a one-person account. A yearly manual access review is the evidence; the free external-access analyzer (F23) stays.
- **F29, the default VPC in Terraform.** Nothing uses a VPC, and adopting one creates a default VPC where none exists. Delete it once when the account is made; F28 already empties its default security group.
- **F30, VPC flow logs.** They would log a VPC that carries no traffic. Ship them with the first VPC a workload creates.
- **F32, SupportAccess.** An Identity Center permission set with AWSSupportAccess meets CIS 1.17 without an IAM role nobody uses; the apply roles already hold `support:*` through PowerUserAccess.
- **F37, CloudTrail Insights.** Pipeline applies and routine refusals drive both the call rate and the error rate, so it would report noise, not signal. GuardDuty is the anomaly switch.
- **F39, a landing-zone mode.** Switching mode would plan the destruction of the trail, detector and recorder, which the organization's baseline policy denies once the account sits in an organizational unit. A mode tested only on mocks would be a gate that passes whatever it is given. The move is its own change (below).

## Single account and landing zone

This module is for one account that is not in a landing zone, or not yet. In a landing zone:

- Member accounts do not duplicate the organization trail or the CIS alarms. The organization trail, in the management account or a CloudTrail delegated administrator, writes to the Log Archive account, and the alarms read its log group centrally.
- GuardDuty, Security Hub, Inspector and an organization Access Analyzer run from a delegated administrator in the security tooling account, which enables every member.
- A member keeps its account settings (F25 to F28, F31), its own key and topic for workload alarms, SecurityBaselineProtect on its apply roles, and an AWS Config recorder, since recorders have no organization-wide auto-enable.
- `verify --mode landing-zone` reads a member that way: the trail family and the detectors report `off (landing-zone mode: the organization covers it)`.
- Until the landing-zone change below, a member account that an organization trail covers should not apply this root: the baseline trail would be a second copy of management events, billed at 2.00 USD per 100,000 (see Prices). `preflight` warns when it finds an organization trail.

Moving this account into the landing zone is its own change, in this order: turn the organization trail on and switch this trail off in the same apply (this module has no trail switch today; that change adds one), settle how the account keeps its Config recorder, then move the account into its organizational unit. Once it is there, the baseline policy denies deleting a trail, detector or recorder.

## Break-glass runbook

When nobody is named in `break_glass_principal_arns`, the break-glass path is the root user, signed in with MFA; the root-usage alarm emails the topic on every call it makes.

Before any emergency: right after the apply that names a user in `break_glass_principal_arns`, the administrator reads the external ID (`tc terraform -chdir=infra/security-baseline output -raw break_glass_external_id`) and stores it with that user's sealed break-glass credentials and MFA device. The only other copy is in this root's state, and in an emergency no one may be able to read that state: reading it takes the administrator's access, which may be what failed.

When BreakGlassAdmin exists:

1. Only an IAM user named in `break_glass_principal_arns` can use it, signed in with MFA within the last hour.
2. Take the external ID from where it was stored with your sealed credentials. It is not a secret: AWS designed external IDs against a confused deputy, not as a password. The controls that matter are MFA within the hour, the one-hour session and the alarm on every use.
3. Assume the role for one hour:

   ```sh
   aws sts assume-role --role-arn arn:aws:iam::<account id>:role/BreakGlassAdmin \
     --role-session-name <your name>-<ticket or reason> --external-id <external id> \
     --serial-number <your MFA device ARN> --token-code <code> --duration-seconds 3600
   ```

4. The break-glass-use alarm emails the alerts topic. Reply to it with the reason, so the record says why.
5. Afterwards, list what the session did from the trail's log group. In CloudWatch Logs Insights on `<service>-shared-cloudtrail`: `filter userIdentity.arn like /BreakGlassAdmin/ | fields eventTime, eventSource, eventName, errorCode | sort eventTime asc`.
6. When a named person leaves, remove their ARN from `break_glass_principal_arns` and apply.

## Known gaps

- **Detectors and settings cover the home Region only.** GuardDuty, Security Hub, Config, Inspector, the analyzer, EBS default encryption, snapshot block public access, the SSM sharing setting, IMDSv2 and the default security group are set in the home Region. The trail and its alarms see every enabled Region. The apply roles have no Region deny yet (the bootstrap README, "Where least privilege stands").
- **It is a deny-list, so a route it does not list stays open.** The apply roles hold PowerUserAccess and the workload roles a broad list of services; the baseline denies the switch-off and tamper actions this page lists, and each route found later gets a deny with a plan-only test, or an entry here that says why there is none. The deny-list on PowerUserAccess was kept over a generated allow-list because a service a workload needs then works without a policy change; a route no audit has found stays open. Denies reach an account only when the administrator re-applies the bootstrap and then the baseline root; `verify`'s `protect` and `default-sg` lines then read them back.
- **The apply and workload roles can still read the trail's events.** The workload boundary and SecurityBaselineProtect deny every other CloudWatch Logs, SNS and EventBridge action on the trail log group, the topic and the findings rules, and the account-level CloudWatch Logs policies, but both kinds of role can still read and query the events, which name people and IP addresses. The deny matches log group names that start `security-baseline-`, so it protects the baseline only while the root's `service` keeps its default.
- **A resource policy on the trail log group is an accepted risk (accepted by the owner, 25 Sep 2026).** IAM authorizes `logs:PutResourcePolicy` against no resource, so only a deny on every resource reaches it, and that would break the HTTP API access logs and Step Functions logging the examples use. Such a policy lets an AWS service write events into the group, for example EventBridge through a rule the role creates; while those events arrive, the trail-delivery alarm stays quiet even if CloudTrail's own delivery has stopped. What still shows it: `verify`'s `trail-delivery` line reads CloudTrail's own last delivery time (`get-trail-status`), not the group's incoming events; `aws cloudtrail validate-logs` proves the trail files in the bucket are unchanged; and the `PutResourcePolicy` call itself is in the trail. What reopens it: IAM giving the action a resource type or a log-group condition key.
- **Index policies on the trail log group are not denied.** IAM gives `logs:PutIndexPolicy` and `logs:DeleteIndexPolicy` no resource type. An index policy changes Logs Insights indexing, not the events or the metric filters.
- **A subscription confirmed by opening its link can be removed without a signature.** SNS then accepts an unsigned Unsubscribe, which IAM never sees, so SecurityBaselineProtect's `sns:Unsubscribe` deny does not stop it; anyone with the subscription's ARN, such as the unsubscribe link in each alert email, can remove the only subscription, and alerts then reach nobody. The administrator confirms with `aws sns confirm-subscription --authenticate-on-unsubscribe true` instead, and `verify`'s `subscription` line fails until `ConfirmationWasAuthenticated` is `true`.
- **Injected metric data can raise a false alarm, not silence one.** SecurityBaselineProtect and the workload boundary deny `cloudwatch:PutMetricData` into the `SecurityBaseline` namespace, but a metric filter on another log group, which PowerUserAccess and the workload boundary's `logs:*` allow, can still publish into it. CloudWatch Logs publishes a filter's metric value "each time a matching log is found", and its default value only "during a period when logs are ingested but no matching logs are found" (Creating metrics from log events using filters, Concepts: https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/MonitoringLogData.html). So the refused-calls filter has no default value and its alarm reads the SampleCount, 5 or more in 300 seconds: the number of matching events, whatever value each carries. The other filters (root use, IAM and bucket policy changes, and break-glass use while that role exists) keep a default value of 0, each match writes 1, and their alarms read the Maximum. A datapoint written from elsewhere, by `PutMetricData` or by another log group's filter, adds a sample or raises a maximum; it never lowers either. Every filter publishes, and every alarm on one reads, unit `Count`, so a datapoint in another unit is aggregated apart and those alarms do not read it; without a unit, the PutMetricAlarm API reference says an alarm over a metric published in more than one unit behaves unpredictably. It can raise a false alarm, never hold a real one down. The dashboard's refused-calls widget reads the SampleCount too. Not yet proved on AWS: that the SampleCount reaches one per match when several refused calls land in the same minute (the local emulator serves no metric filters). Check it on the first apply: five refused calls one after another within one minute, then the SampleCount and the alarm's Action history. If it counts fewer, the alarm goes back to the Sum and the injection gap reopens.
- **Security Hub has control gaps in ap-southeast-6** (no IAM, GuardDuty, Inspector, WAF, CloudFront or HTTP API controls), and **Amazon Inspector is not offered there**; the plan refuses `inspector_enabled = true` in that Region.
